### 1.2 초당 제한

**공식 문서에서 초당(TPS, QPS) 제한 수치를 찾지 못했다.** 확인한 근거는 다음과 같다.

- <https://developers.kakaomobility.com/price/> 는 일일 제공량과 단가만 제시하고, 초당 제한을 언급하지 않는다.
- <https://developers.kakao.com/docs/ko/getting-started/quota> 의 `요청 수 제한` 절에는 카카오 로그인 토큰 발급 제한만 기재되어 있다. 원문을 인용한다.
  > | API | 제한량 |
  > |---|---|
  > | 카카오 로그인: 토큰 요청 API와 토큰 갱신 API로 발급 가능한 토큰 수(사용자 1명 기준) | 액세스 토큰: 10분당 20개 / 리프레시 토큰: 60분당 30개 |
- <https://developers.kakaomobility.com/guide/navi-api/reference> 의 응답 코드 표에는 경로 탐색 결과 코드와 교통 정보 상태 코드만 정의되어 있고, 호출 빈도 제한 코드가 없다.

데브톡에는 길찾기 API를 연속으로 50회 정도 호출했을 때 `API limit has been exceeded` 오류를 받았다는 사용자 문의(<https://devtalk.kakao.com/t/api-api-limit-has-been-exceeded/128538>)가 있으나, 공식 수치가 답변으로 제시되지는 않았다. 따라서 초당 제한은 미확인 상태로 남겨 두고, 수집기에서는 호출 간격을 두고 오류 발생 시 지수 백오프로 재시도하는 방식을 유지해야 한다.

### 1.3 쿼터를 소진했을 때 돌아오는 HTTP 응답

두 가지 응답 형태가 문서에 모두 존재하므로 수집기는 둘 다 처리해야 한다.

**첫째, 카카오맵(로컬) API는 429를 반환한다.** 출처: <https://developers.kakao.com/docs/ko/kakaomap/common>

> Q. 429 Too Many Request 에러가 발생해요.  
> 카카오맵 API는 앱별로 무료로 제공하는 쿼터가 있습니다. 무료 제공량을 모두 소진한 경우, 429 에러가 발생합니다. 무료 제공량 외에 더 많은 제공량이 필요한 경우, 유료 API를 설정해 추가 API를 호출할 수 있습니다.

**둘째, 공통 REST API 에러 코드 표에서는 상태 코드 400과 에러 코드 -10을 반환한다.** 출처: <https://developers.kakao.com/docs/ko/rest-api/error-code>

> | 에러 코드 | 상태 코드 | 원인 | 해결 방법 |
> |---:|---:|---|---|
> | -10 | 400 | 허용된 요청 회수를 초과한 경우 | 쿼터 확인 후 쿼터 범위 내로 호출 조정, 필요시 데브톡으로 제휴 문의 |
> | -11 | 400 | 일 한도 또는 월 한도 금액을 초과한 유료 API를 호출한 경우 | 한도 확인 후 한도 금액 상향 |

즉 HTTP 429가 오거나, HTTP 400 본문에 `code: -10`이 담겨서 올 수 있다. 유료 API를 설정한 뒤 금액 한도를 초과하면 `code: -11`이 온다.

### 1.4 쿼터 초기화 시각

**공식 문서에는 초기화 시각이 명시되어 있지 않다.** 카카오 운영자 계정의 데브톡 답변만 확인했다. 출처: <https://devtalk.kakao.com/t/topic/149116>

> 질문(지누8494, 2026-04-06): 무료 쿼터를 다 써서 429가 발생했을 때 매일 언제 초기화되는지, KST 00:00:00인지 UTC 00:00:00인지, 아니면 최근 24시간 기준인지 궁금합니다.  
> 답변(tim.l, 2026-04-06): "매일 자정에 리셋됩니다"

답변에 표준시가 적혀 있지 않으므로, KST 자정으로 가정하되 실제 수집 첫날에 잔여 쿼터가 회복되는 시각을 로그로 확인해서 검증해야 한다. 롤링 24시간 방식이 아니라 고정 시각 초기화라는 점은 답변으로 확인되었다.

### 1.6 약 40,000개 방향쌍을 수집하는 데 필요한 일수

| 항목 | 값 |
|---|---:|
| 필요한 방향쌍 총량(추정) | 약 40,000건 |
| 자동차 길찾기 일일 무료 제공량 | 10,000건 |
| 무료 쿼터만 사용할 경우 필요 일수 | **4일** |
| 재시도와 검증 호출 여유를 10% 더할 경우 | **5일** |
| 전량을 유료로 처리할 경우 비용 | 40,000건 × 8원 = 320,000원 |
| 무료 쿼터를 매일 소진하고 초과분만 유료로 처리해 하루에 끝낼 경우 | 30,000건 × 8원 = 240,000원 |

수원시 `41110`의 입지계산 필수 방향쌍이 1,683개였으므로, 31개 시·군의 평균이 그 수준이면 총량은 약 52,000건이 되고 무료 쿼터만으로는 6일이 걸린다. 40,000건 기준으로는 4일이고, 하루에 6개에서 7개 시·군씩 나누어 수집하는 일정이 된다. 월간 무료 제공량은 전체 API 합산 3,000,000건이므로 월간 한도는 제약이 되지 않는다.

수집기는 시·군 단위로 중단하고 재개할 수 있어야 한다. `road_times_manifest.json`에 `required_pair_count`와 `completed_pair_count`를 기록하는 현재 방식을 그대로 유지하면, 쿼터가 소진되어 중단된 다음 날에 남은 시·군부터 이어서 수집할 수 있다.

### 2.2 원본 시군코드 오류를 발견했으므로 반드시 주의해야 한다

원본의 `SIGUN_CD` 필터는 남양주시를 정상적으로 구분하지 못한다.

- `SIGUN_CD=41360`(남양주시)으로 조회하면 응답이 0행이다.
- `SIGUN_CD=41630`(양주시)으로 조회하면 54,481행이 오는데, 이 안에 남양주소방서 행 37,876건과 양주소방서 행 16,605건이 함께 들어 있다.

따라서 시·군 배정은 원본의 시군코드가 아니라 **출동소방서명**을 기준으로 해야 한다. 후처리 스크립트는 이 기준을 따르며, 인구 규모로 검산해도 남양주시(72.7만 명)에 37,876건, 양주시(29.8만 명)에 16,605건이 배정되는 결과가 타당하다.

### 3.2 모델의 4개 유형으로 묶은 비율 제안

**아래 매핑은 제안일 뿐이며 확정된 분류가 아니다.** 원본에는 증상 코드만 있고 중증도나 진단 분류가 없으므로, 어떤 증상을 어느 유형에 넣을지는 모델 설계자가 판단해서 확정해야 한다.

| 모델 유형 | 포함시킨 증상 | 건수 | 전체 대비 | 기재행 대비 |
|---|---|---:|---:|---:|

이 매핑을 사용할 때 반드시 함께 고려해야 하는 한계는 다음과 같다.

- **원본에 사고종별 열이 없다.** 교통사고와 추락은 증상이 아니라 사고 유형이므로, 이 자료에서는 외상 계열 증상으로만 간접 추정할 수 있다. 따라서 위 표의 trauma 12.49%는 실제 외상 환자 비율보다 낮게 나올 가능성이 크다. 발생장소 분류에서 `도로외교통지역`이 기재행의 11.98%, `도로`가 7.92%를 차지하므로, 교통 관련 출동의 규모는 발생장소 쪽으로 보완해서 추정하는 편이 낫다.
- **호흡 계열 증상을 담을 유형이 없다.** 호흡곤란은 기재행의 4.73%로 심정지보다 많은데도 4개 유형 체계에서는 minor로 떨어진다. 중증도 기준으로는 부적절하므로, 유형을 5개로 늘리거나 minor 안에서 중증 가중치를 따로 두는 방안을 검토해야 한다.
- **`기타통증`과 `기타`가 기재행의 29.14%를 차지한다.** 이 두 범주를 어떻게 배분하는지에 따라 minor 비율이 크게 달라지므로, 민감도 분석 대상으로 삼아야 한다.
- **실신을 cardiac에 넣은 것은 판단이 개입된 결정이다.** 실신은 심혈관 원인일 수도 있고 아닐 수도 있으므로, 제외하면 cardiac은 3,345건(기재행 대비 6.50%)으로 줄어든다.
- 미기재 32.96%를 어떻게 처리할지도 결정해야 한다. 기재행의 비율을 그대로 적용해 미기재 행에 배분하는 방법과, 미기재 행을 별도 유형으로 두는 방법 중에서 선택해야 한다.

### 3.4 시간대 열이 없다는 사실

**이 데이터셋에는 신고시각, 출동시각, 현장도착시각처럼 시각을 담은 열이 전혀 없다.** 제공되는 열은 집계년도, 시군명, 출동소방서, 출동안전센터, 환자연령, 환자성별, 외국인여부, 국적, 구급처종명, 환자증상1의 10개뿐이며, 시간 단위는 연도가 가장 작은 단위다. 따라서 시간대별 수요 곡선이나 요일별 변동은 이 자료로 만들 수 없다. 월 단위 계절성은 이미 확보한 `data/processed/calibration/nfa_gyeonggi_monthly_seasonality_2020_2023.csv`로 처리하고, 시간대별 변동이 필요하면 별도 출처를 찾아야 한다.

## 5. 경기데이터드림 파일 다운로드 가능성 정리

인수인계 문서가 남긴 과제, 즉 Sheet 다운로드 버튼의 요청 경로를 추적하는 작업은 다음과 같이 마무리되었다.

- 다운로드 버튼이 호출하는 경로는 `/js/data/service/selectSheet.js`에 있다. 이 스크립트는 숨은 폼의 질의 문자열을 붙여서 `/portal/data/sheet/downloadSheetData.do?<queryString>`을 iframe의 `src`로 지정한다.
- 이 경로를 CSRF 토큰까지 포함해 호출해도 `구급활동 현황`에서는 오류 화면만 돌아온다. 즉 **로그인 없이 동작하는 파일(Sheet/CSV) 다운로드 주소는 존재하지 않는다.**
- 대신 같은 화면이 표를 그릴 때 사용하는 `POST /portal/data/sheet/searchSheetData.do`가 로그인 없이 전체 행을 JSON으로 반환한다. 결과적으로 파일 다운로드보다 이 경로가 더 완전한 자료를 제공한다.
- Open API 탭(`infSeq=2`)은 여전히 요청주소와 출력 스키마가 비어 있으므로, 경기데이터드림 인증키를 사용할 필요가 없다. `blocked_sources.json`에 기록된 `official_endpoint_specification_not_publicly_exposed` 상태는 변하지 않았다.

`scripts/prepare_municipal_dispatch_rates.py`는 출동소방서명을 시·군 코드로 바꾸는 표를 스크립트 안에 명시적으로 들고 있다. 표에 없는 소방서명이 입력에 나타나면 그 이름을 출력하면서 즉시 종료하므로, 소방서가 신설되거나 이름이 바뀌면 조용히 누락되지 않고 실패한다. 집계년도가 두 개 이상 섞여 있을 때에도 같은 방식으로 실패한다.
